**WS-OPP-10**, 2026-09-01 product plan. Probe run 2026-09-02 05:44 to 05:46 UTC
from the scraper host (`zhujimmy` macOS, Python 3.13, `coverage_connectors`
HTTP layer).

> **Path note.** The item names `docs/research/talnet-2026-09.md`. That whole
> directory is gitignored, deliberately and bluntly, because this repo is
> public and `docs/research/` holds real people's names and the founder's own
> target list (`.gitignore` line 77, "Scrubbed from history 2026-08-02; these
> rules stop them coming back"). A document nobody else can check is not
> evidence, and `health.WALL_EVIDENCE_DOC` cites this path from code, so the

## Why this document exists

Two Grade A observations taken on the same night disagreed.

- `research-ats-lifecycle.md` Q1 and Q6: Morgan Stanley's tal.net campus board
  is reachable with plain curl and a browser user agent, HTTP 200, 68
  vacancies, and the standing "bot-walled" note is wrong.
- `research-eligibility-language.md` §1 and its harvesting note: `*.tal.net`
  serves an ALTCHA proof-of-work challenge with zero job content, covering
  Morgan Stanley, Bank of America campus, Jefferies and Evercore.

`audit-opportunities.md` §B1 measured the product's own experience over its run
history and found all five walled at least once: Nomura 18 runs, Morgan Stanley
12, Evercore 10, Jefferies 5, Bank of America 2 and flapping.

Nobody could settle it by re-reading the files, so the plan made one recorded
probe the gate on every other tal.net item.

## What was done

One request per cell. Five boards (the jobs board of each tenant), two user
agents, cookie jar off and on: 20 requests, four per host, spaced two seconds
apart. No pagination was followed, no posting page was opened, nothing was
written to the database. This is a probe, not a scrape.

- **project** user agent is `coverage_connectors.http.USER_AGENT`, the honest
  one the scraper actually sends:
  `coverage-connectors/0.1 (+https://coverage.app; deterministic ATS/board fetcher)`.
- **browser** user agent is a current desktop Chrome string. It is here as an
  experimental arm, to answer whether the user agent is what decides the
  outcome. It is not what the connector sends and this document is not a
  proposal that it should be.
- Vacancy counts come from `talnet._parse_table` and `talnet._parse_cards`, the
  connector's own parsers, so the number means the same thing here as it does
  in ingest.

Every request verified TLS against certifi's roots, which is the fetch layer's
default since 2026-09-01.

## What it settles

**Neither research file was right about `*.tal.net` as a platform, because
there is no platform-wide answer. Oleeo Protect is a per-tenant setting.**

1. **Four of the five boards are reachable, today, with the project's own
   honest user agent.** Bank of America, Morgan Stanley, Evercore and Jefferies
   all return a real board carrying real vacancy markup. So
   `research-eligibility-language.md` §1's "`*.tal.net` serves a challenge with
   zero job content" is wrong as a statement about the domain; it was true of
   whatever tenant it was measured against.
2. **One board is walled, and it is Nomura**, which is the one tenant neither
   research file names. `research-ats-lifecycle.md` Q1 was right about Morgan
   Stanley specifically and wrong to generalise from it to the standing note.
3. **The user agent is not the variable.** Every board returned the same status
   and the same vacancy count under both. The 14-byte difference between the
   project and browser responses is the user agent echoed back into the page,
   nothing more. Nomura serves the challenge to a browser string exactly as it
   serves it to ours, so there is no version of "send a browser user agent" that
   opens that board. Nothing here would be improved by pretending to be a
   person, which is the answer that matters, because the alternative would have
   crossed from reading a public page into defeating an employer's control.
4. **A cookie jar changes nothing.** Byte-identical responses in all ten pairs.
   No board sets a cookie that turns the challenge off, which is what an ALTCHA
   proof-of-work challenge is supposed to mean.
5. **The product's own runs already agreed with this.** `walled_boards()` on
   the live database returns exactly one firm, Nomura, walled since
   2026-09-01 15:30 UTC with 48 open rows frozen behind it. §B1's larger counts
   are run history, not the current state: Morgan Stanley, Evercore and
   Jefferies stopped erroring before this probe was taken.

## What follows

- **Nomura stays walled and stays configured.** It is one tenant's deliberate
  anti-bot setting, so it will fail every run until they change their mind, and
  no edit on our side fixes it. `talnet.bot_challenge_reason` already names it
  correctly and `health.walled_boards` already reports it once, loudly, and then
  quietly. Do-not-build register §5.2 item 13 stands: no challenge solver, for
  one board or any number of them.
- **The other four are ordinary boards and their code paths are ordinary.** The
  connector needed no change to reach them. WS-OPP-09 is therefore free to
  proceed as a parse, and its Nomura fixture is built from rows this board
  delivered on 2026-07-23 rather than from a fetch we cannot make.
- **The "bot-walled" line in `health_report()` now cites this document**, so the
  standing condition points at its evidence instead of at a memory.

## Two things this probe measured but did not answer

Recorded here rather than acted on, because acting on either would have been a
guess (P1) and neither is in WS-OPP-10's scope.

1. **Three of the four reachable boards returned exactly 50 vacancies.** Bank of
   America, Morgan Stanley and Jefferies all stopped at 50; Evercore, the small
   board, returned 9. Fifty is the card layout's page size, and
   `_fetch_card_pages` follows the `next_links` nav for that layout and reports
   `truncated` when it cannot finish. The table layout does not paginate at all,
   on the stated grounds that "Morgan Stanley returns 1,076 rows in one
   response" (`talnet.py` module docstring). Morgan Stanley returned 50 here.
   The boards catalog's own note from 2026-09-01 reads Bank of America's board 1
   as 148 vacancies off its Atom feed, against 50 in the HTML.

   If the table boards now page at 50, then every table-layout fetch is a
   partial list read as a complete one, and ingest closes what it does not see.
   That would be a real defect and a larger one than anything WS-OPP-10 was
   asked about. **It is not settled by this probe** — the probe did not save the
   response bodies, so whether those pages carry a `next_links` nav is unknown.
   It needs its own probe: one fetch per table board, keeping the body, grepping
   for `next_links`. Do not change pagination behaviour before that.

   **Settled 2026-09-02 — see `docs/talnet-pagination-2026-09.md`.** That probe
   was run with the bodies kept. The table boards do carry the nav: Morgan
   Stanley serves 50 rows under its own "67 results match", Bank of America 50
   under "148 results match!", both with the identical
   `<span class="next_links"><a href="?start=50">`. It was a real defect, and 67
   live roles on page two of those two boards had never reached the database.
   Both branches walk the nav now.

2. **`robots.txt` was not consulted for these hosts and is not consulted by the
   connector fetch path.** `core/robots.py` guards `enrich_postings` and
   `fetch_firm_logos`; `coverage_connectors.http` has no robots check of its
   own. That gap is decision D-20's territory and WS-OPS-13's item, and this
   document does not pre-empt either.
